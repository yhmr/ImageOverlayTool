# テストガイドライン

このガイドラインは、テストコードを保守しやすく、振る舞い中心に保つための基準です。

## 基本ルール

1. 内部実装ではなく、振る舞いを検証する。
2. 1テストにつき、失敗理由は明確に1つにする。
3. 各テストは `Arrange -> Act -> Assert` の順序を守る。
4. OS/ランタイム差に強い、安定したアサーションを使う。
5. 暗黙の共有状態より、明示的なセットアップを優先する。

## 単体テストのルール

1. まず外部から観測できる結果を検証する。
2. 依存先の呼び出し検証は、それ自体が振る舞いの一部である場合に限定する。
3. `mock.calls[0][0]` のような内部配列への直接アクセスはしない。
4. 代わりに `toHaveBeenCalledWith`、`toHaveBeenNthCalledWith`、または明示的にキャプチャしたコールバック変数を使う。
5. 実装詳細に強く結びついた検証（区切り文字の厳密一致、一時的なID、業務上意味のない呼び出し順）を避ける。

## 結合テストのルール

1. 可能な範囲で実装を使い、モジュール/リポジトリ/IPC境界をまたぐ相互作用を検証する。
2. モックは本当に外部依存のもの（OSダイアログ、ネットワーク、自分たちが管理していないFS副作用）に限定する。
3. 内部配線ではなく、最終結果（永続化データ、返却値、観測可能な状態）を検証する。

## 命名ルール

1. 単体テスト: `*.spec.ts` / `*.spec.tsx`
2. 結合テスト: `*.int-test.ts` / `*.int-test.tsx`
3. テスト名は「条件」と「期待する振る舞い」を表現する。例:
   - `save dialog がキャンセルされた場合は null を返す`
   - `import 後に正規化済み設定を永続化する`

## レビューチェックリスト

1. このテストは業務的に1つの理由だけで失敗するか？
2. 実装の軽微なリファクタで壊れないか？
3. OS依存の挙動を題材にしていない限り、アサーションはOS非依存か？
4. `mock.calls[...]` のインデックスアクセスを置き換えられないか？
5. 利用者/呼び出し側が見る振る舞いへの信頼性を高めているか？
